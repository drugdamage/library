# Access и Python: сравнение БД «Библиотека»

## Предмет сравнения

Сравниваются две реализации системы учёта библиотеки: Microsoft Access (таблицы, запросы, формы, макросы/VBA) и Python + PyQt6 + SQLite (SQL, функции, обработчики событий). Интерфейс и пользовательские действия должны быть сопоставимы, чтобы сравнивать способ реализации.

Источники по прежней работе: три документа в `docs/` и исходный файл `Библиотека.accdb`. 18.11.2026 прочитаны таблицы и имена объектов Access без запуска форм и макросов. Ниже отделены результаты этого чтения, сведения методички и проверки, требующие запуска Access. Результаты Python проверяются локальными тестами. Временные замеры обеих версий пока не проводились.

## Сопоставление задач

### Создание таблиц и простой формы

**Access:** Конструктор таблиц, связи, мастер форм, привязка полей.

**Python / PyQt6 / SQLite:** SQL-схема и код виджетов, заполнение таблицы вручную.

**Оценка:** Для типовой формы Access требует меньше ручного кода; это оценка подхода, время не измерено.

### Печатные отчёты

**Access:** Встроенные мастер и конструктор отчётов.

**Python / PyQt6 / SQLite:** Нужно отдельно реализовать подготовку и печать.

**Оценка:** Здесь Access удобнее; в Python сейчас есть таблица и CSV, печати ещё нет.

### Поиск при вводе

**Access:** В «Доработки 2» уже есть `On Change`, `TempVars`, `Requery`, фильтр наличия.

**Python / PyQt6 / SQLite:** `textChanged`, `search_books`, нормализация русских букв и поиск всех введённых слов. Символы `%` и `_` трактуются буквально. Поддерживается поиск экземпляра по инвентарному номеру.

**Оценка:** Реализуемо в обеих системах; живой поиск не преимущество Python.

### Поиск и выбор читателя

**Access:** В исходной базе есть форма `фЧитатели`; поведение её поиска и выбора при изменении фильтров пока не проверено.

**Python / PyQt6 / SQLite:** Обе рабочие формы используют `search_readers` и общий элемент `ReaderSearch`. Билет ищется по точному номеру, ФИО — по всем словам независимо от порядка, телефон — отдельным режимом без учёта оформления. Первая найденная запись автоматически не выбирается. Поиск книг не меняет получателя.

**Оценка:** Общая реализация обеспечивает одинаковые правила поиска в нескольких формах. Точность выбора проверяется отдельно от интерфейса и при взаимодействии виджетов. Сопоставимый сценарий в Access ещё не проверен.

### Обновление сводки

**Access:** В «Доработки 2»: `On Activate`, `DCount`, `Requery`.

**Python / PyQt6 / SQLite:** `HomePage.refresh`, `get_stats` при возврате в меню.

**Оценка:** Одинаковый результат разными средствами.

### Изменение срока выдачи

**Access:** Выражение расчёта даты и действия формы выдачи в готовой базе пока не проверены.

**Python / PyQt6 / SQLite:** `LOAN_DAYS`, параметр `days`, выбор срока в форме.

**Оценка:** Python позволяет проверить правило без открытия формы; изменение Access ещё не выполнено.

### Атомарность выдачи и журнала

**Access:** Доступны DAO `BeginTrans`, `CommitTrans`, `Rollback`; наличие их в готовой базе не проверено.

**Python / PyQt6 / SQLite:** `BEGIN IMMEDIATE`, обновление и журнал в одном `with connect()`.

**Оценка:** Транзакции есть в обоих подходах. В Python откат при сбое журнала подтверждён автотестом.

### Повторная выдача и возврат

**Access:** Ограничения при повторной выдаче и возврате в готовой базе пока не проверены.

**Python / PyQt6 / SQLite:** Проверки состояния в `issue_book`, `return_book`, явный выбор записи и подтверждение операции. Возврат дополнительно сверяет идентификатор выдачи, чтобы устаревший список не закрыл новую выдачу того же экземпляра.

**Оценка:** Python-сценарии проверены; результаты Access ожидают проверки.

### Книга с несколькими авторами и экземплярами

**Access:** В методичке отдельные связанные формы книг, связей и экземпляров.

**Python / PyQt6 / SQLite:** Одна функция `add_book` и форма; все записи в одной транзакции.

**Оценка:** Python объединяет несколько связанных действий в одной функции. Аналогичная реализация возможна в VBA.

### Регистрация читателя

**Access:** Связанная форма, обязательные поля и правила проверки.

**Python / PyQt6 / SQLite:** Отдельная форма регистрации и проверки в `add_reader`: обязательные поля, явная дата рождения, формат телефона и совпадение с уже зарегистрированным читателем.

**Оценка:** Access проще для типового ввода; Python удобно проверять повторно без GUI.

### Карточка читателя

**Access:** Найдена `фЧитатели`; состав связанных данных и наличие аналогичной карточки ещё нужно проверить в Access.

**Python / PyQt6 / SQLite:** `get_reader_card` получает данные по номеру билета; диалог показывает текущие книги и личный журнал.

**Оценка:** Карточка реализована в Python без изменения схемы данных. Наличие аналогичной функции в готовой Access-базе пока не установлено.

### Экспорт

**Access:** Access имеет средства экспорта; конкретный результат готовой базы не проверен.

**Python / PyQt6 / SQLite:** Общая функция CSV для четырёх отчётов, BOM, `;`, защита текстовых ячеек от формул.

**Оценка:** Python даёт явный контроль формата; уникальной возможностью экспорт не является.

### Резервная копия

**Access:** Процедура резервирования готовой Access-базы пока не проверена.

**Python / PyQt6 / SQLite:** `sqlite3.Connection.backup`, отдельный файл, без перезаписи исходника.

**Оценка:** Создание копии автоматизировано в Python; преимущество по времени не измерено.

### Регрессионная проверка

**Access:** Для сопоставимых автопроверок нужен отдельный VBA/внешний сценарий.

**Python / PyQt6 / SQLite:** `unittest`, временные БД, проверки успеха и отказов одной командой.

**Оценка:** В текущем Python-проекте правила проверяются независимо от формы.

### Контроль изменений

**Access:** Объекты Access находятся внутри файла базы; сравнение требует дополнительных приёмов/экспорта.

**Python / PyQt6 / SQLite:** SQL, логика и формы в текстовых файлах Git.

**Оценка:** В Python проще просмотреть конкретное изменение и повторить тесты; это оценка сопровождения.

## Организация логики Python

`database.py` не зависит от Qt: выдачу, возврат, регистрацию и пополнение фонда вызывают формы и тесты. Изменение правила можно проверить на временной базе независимо от интерфейса. В `reports.py` четыре отчёта описаны единообразно: источник данных и список полей. Один экспорт используется всеми отчётами. В `ui/common.py` таблицы, сортировка, поиск читателей и сообщения переиспользуются рабочими формами из `ui/workflows.py`. Даты форматируются для чтения, а сортировка и CSV используют исходные значения.

Для проверки отката при сбое журнала тест создаёт временный триггер, который отклоняет вставку. После неудачной выдачи экземпляр остаётся свободным, после неудачного возврата — выданным. Код проверки хранится в Git и повторяется после каждого изменения. Это преимущество выбранной структуры проекта и удобства инструментов Python; аналогичную надёжность можно реализовать и в Access с VBA/DAO.

Для карточки читателя функция `get_reader_card(reader_id)` читает связанные данные в общей транзакции чтения, а интерфейс выводит их в двух вкладках. Проверки подтверждают, что возврат убирает книгу из текущих, сохраняет историю прежнего читателя и не смешивает её с историей следующего заёмщика того же экземпляра. Старые сроки в журнале не подсвечиваются как текущая просрочка. Реализация использует существующие таблицы и сохраняет структуру главного меню.

**Access:** Сценарий пока не проверен.

### Совпадение оформления

**Python:** Восстановлены четыре кнопки и порядок переходов.

**Access:** Нужны снимки готовых форм.

## Ограничения и предварительный вывод

Access удобен для быстрого создания типовых связанных форм и печатных отчётов. Python требует больше кода и ручной сборки интерфейса, зато в этом проекте логика отделена от окон, повторно используется и автоматически проверяется. Вывод о скорости, полной функциональной эквивалентности или точном совпадении внешнего вида пока не обоснован.

Учебные роли не защищают файл БД от прямого изменения, SHA-256 без соли не подходит для эксплуатационного хранения паролей. Многопользовательская нагрузка, миграция данных из Access и готовый установщик не исследовались.
