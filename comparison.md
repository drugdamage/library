# Access и Python: сравнение БД «Библиотека»

## Что сравниваем

Одну задачу учёта библиотеки в двух реализациях: Microsoft Access (таблицы, запросы, формы, макросы/VBA) и Python + PyQt6 + SQLite (SQL, функции, обработчики событий). Интерфейс и пользовательские действия должны быть сопоставимы, чтобы сравнивать способ реализации.

Источники по прежней работе: три документа в `docs/`. Готового файла `.accdb` в репозитории нет. Поэтому ниже сведения Access подтверждены методичкой или документацией Microsoft, но не запуском сданного приложения. Результаты Python проверяются локальными тестами. Временные замеры обеих версий пока не проводились.

## Сопоставление задач

| Задача | Access | Python/PyQt6/SQLite | Вывод и статус |
|---|---|---|---|
| Создать таблицы и простую форму | Конструктор таблиц, связи, мастер форм, привязка полей | SQL-схема и код виджетов, заполнение таблицы вручную | Для типовой формы Access требует меньше ручного кода; это оценка подхода, время не измерено |
| Сделать печатный отчёт | Встроенные мастер и конструктор отчётов | Нужно отдельно реализовать подготовку и печать | Здесь Access удобнее; в Python сейчас есть таблица и CSV, печати ещё нет |
| Поиск при вводе | В «Доработки 2» уже есть `On Change`, `TempVars`, `Requery`, фильтр наличия | `textChanged`, `search_books`, пользовательская SQL-функция `py_lower` для кириллицы | Реализуемо в обеих системах; живой поиск не преимущество Python |
| Обновление сводки | В «Доработки 2»: `On Activate`, `DCount`, `Requery` | `HomePage.refresh`, `get_stats` при возврате в меню | Одинаковый результат разными средствами |
| Изменение срока выдачи | Проверить выражение даты и действия формы выдачи в готовой базе | `LOAN_DAYS`, параметр `days`, выбор срока в форме | Python позволяет проверить правило без открытия формы; изменение Access ещё не выполнено |
| Атомарность выдачи и журнала | Доступны DAO `BeginTrans`, `CommitTrans`, `Rollback`; наличие их в готовой базе не проверено | `BEGIN IMMEDIATE`, обновление и журнал в одном `with connect()` | Транзакции есть в обоих подходах. В Python откат при сбое журнала подтверждён автотестом |
| Повторная выдача и возврат | Проверить ограничения макросов/кода на копии `.accdb` | Проверки состояния в `issue_book`, `return_book` | Python-сценарии проверены; результаты Access ожидают проверки |
| Книга с несколькими авторами и экземплярами | В методичке отдельные связанные формы книг, связей и экземпляров | Одна функция `add_book` и форма; все записи в одной транзакции | Демонстрация гибкости композиции действий в Python, но аналог возможен в VBA |
| Регистрация читателя | Связанная форма, обязательные поля и правила проверки | Виджеты формы + проверка обязательных полей и даты в `add_reader` | Access проще для типового ввода; Python удобно проверять повторно без GUI |
| Экспорт | Access имеет средства экспорта; конкретный результат готовой базы не проверен | Общая функция CSV для четырёх отчётов, BOM, `;`, защита текстовых ячеек от формул | Python даёт явный контроль формата; уникальной возможностью экспорт не является |
| Резервная копия | Процедуру резервирования готовой Access-базы проверить отдельно | `sqlite3.Connection.backup`, отдельный файл, без перезаписи исходника | Рабочая демонстрация программной автоматизации; преимущество по времени не измерено |
| Регрессионная проверка | Для сопоставимых автопроверок нужен отдельный VBA/внешний сценарий | `unittest`, временные БД, проверки успеха и отказов одной командой | Наиболее наглядное преимущество организации текущего Python-проекта: правила проверяются независимо от формы |
| Контроль изменений | Объекты Access находятся внутри файла базы; сравнение требует дополнительных приёмов/экспорта | SQL, логика и формы в текстовых файлах Git | В Python проще просмотреть конкретное изменение и повторить тесты; это оценка сопровождения |

## Где именно видна гибкость Python

`database.py` не зависит от Qt: выдачу, возврат, регистрацию и пополнение фонда вызывают формы и тесты. Изменение правила можно проверить на временной базе без кликов. В `reports.py` четыре отчёта описаны единообразно: источник данных и список полей. Один экспорт используется всеми отчётами. В `ui/workflows.py` таблицы, сортировка и сообщения переиспользуются разными формами.

Показательный эксперимент — авария записи журнала: тест создаёт временный триггер, который отклоняет вставку. После неудачной выдачи экземпляр остаётся свободным, после неудачного возврата — выданным. Код проверки хранится в Git и повторяется после каждого изменения. Это преимущество выбранной структуры проекта и удобства инструментов Python; аналогичную надёжность можно реализовать и в Access с VBA/DAO.

## Что показать преподавателю за 5–10 минут

1. Войти как `lib / 1111`. Показать четыре кнопки, недоступное администрирование и исходную сводку.
2. «Отчёты» → «Поиск книг»: ввести `СТРУ`, включить «Только доступные», выбрать жанр; сравнить с формой поиска Access.
3. «Выдача»: найти читателя, выбрать свободный экземпляр и срок 21 день. Запомнить инвентарный номер. Выдать и проверить сводку/отчёт.
4. Снять фильтр наличия, найти этот экземпляр, повторить выдачу: получить отказ. В «Отдача» принять его; проверить две записи журнала.
5. Зарегистрировать читателя; показать проверку пустых полей и ограничение даты рождения.
6. Войти как `admin / 1234`, добавить книгу с двумя авторами и тремя экземплярами. Найти их в поиске. Создать резервную копию в отдельный файл.
7. Открыть должников и полный журнал, сохранить CSV. Продемонстрировать те же данные в Access, если файл доступен.
8. Выполнить `python -m unittest discover -s tests -v`. Объяснить тест отката журнала и связь тестов с изменением правил.

Демонстрация изменяет базу. Для повторяемого показа использовать отдельную копию проекта/БД; не удалять рабочую `library.db`. Автотесты сами создают временные базы.

## Протокол сравнительной проверки

Заполняется после запуска обеих программ на одинаковых исходных данных. Для времени разработки фиксировать начальное состояние и точное изменение; для скорости — одинаковую задачу и объём данных. Автотест не заменяет замер действий оператора.

| Эксперимент | Результат Python | Результат Access | Время Access / Python |
|---|---|---|---|
| Поиск `СТРУ`, доступные | 2 экземпляра на исходных тестовых данных | По методичке также 2; запуск не выполнен | Не измерено |
| Выдача → повторная выдача → возврат | Успех → отказ → успех, две новые записи журнала | Не проверено на `.accdb` | Не измерено |
| Сбой журнала | Частичные изменения откатываются | Не проверено на `.accdb` | Не измерено |
| Добавить книгу с несколькими авторами | Одна транзакция, проверяется тестом | Не проверено на `.accdb` | Не измерено |
| Изменить срок 14 → 21 | Параметр формы передаётся функции, дата проверяется тестом | Не проверено на `.accdb` | Не измерено |
| CSV одного отчёта | Проверяется содержимое, заголовки и кодировка | Не проверено на `.accdb` | Не измерено |
| Совпадение оформления | Восстановлены четыре кнопки и порядок переходов | Нужны снимки готовых форм | Не измерено |

## Ограничения и предварительный вывод

Access удобен для быстрого создания типовых связанных форм и печатных отчётов. Python требует больше кода и ручной сборки интерфейса, зато в этом проекте логика отделена от окон, повторно используется и автоматически проверяется. Это основной тезис работы. Вывод о скорости, полной функциональной эквивалентности или точном совпадении внешнего вида пока не обоснован.

Учебные роли не защищают файл БД от прямого изменения, SHA-256 без соли не подходит для эксплуатационного хранения паролей. Многопользовательская нагрузка, миграция данных из Access и готовый установщик не исследовались.
